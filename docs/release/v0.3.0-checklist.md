### 8.5 Release-blocking defects found by these gates

Each was fixed through its own pull request, with a regression test, CI, and a re-run of the
gate that found it. The release target moved to the merge of each.

| # | Defect | Found by | Fixed in |
| --- | --- | --- | --- |
| 1 | Four console files were **not `dart format` clean** — `flutter analyze` does not check formatting and the CI job ran `analyze` and `test` but not `format`, so a documented gate was never enforced | the format gate | PR #44 (which also **added the format step to CI**) |
| 2 | The operator identity gate claimed *"Production deployments integrate with Google Cloud Identity Platform"* — **false**, operator-facing, and contradicted the owner decision that accounts/RBAC are out of scope | browser QA | PR #45 |
| 3 | The corpus panel said a new document *"would be stored but never read"* — the **retired read-ceiling behaviour**, contradicting the release notes on a headline item | browser QA | PR #46 |
| 4 | The backup script **failed on any database with an empty collection**, and its count read was mangled by Windows PowerShell 5.1 so the manifest recorded **0 documents for every collection** — making the restore's count comparison **vacuous** | the backup/restore drill | PR #47 |

**A verification error worth recording**: the first Compose run reported `0.2.0` because
`docker compose up` reused an **11-hour-old `cerberus-api:latest` image** from a previous
session. Rebuilding with `--no-cache` reported `0.3.0`. The image is built from source, so
this was a stale local image rather than a product defect — but it is why the runtime version
is checked on a freshly built image rather than assumed.

### 8.8 Live OpenAI call

**No fresh live call was made, and none was required.** `apps/api/src/ai/` and
`apps/api/src/config.ts` are **byte-identical** across the whole cycle (`git log
ccfcead..HEAD` over those paths is empty; their last change predates the cycle). Provider
request construction, the parser/provider boundary, model configuration and the relevant
persistence boundary are unchanged, so the existing evidence remains representative.

The one provider-adjacent change was the **ingest write order** — the assessment is now
persisted before the status change and the notification — which is persistence ordering, not
request construction. It is covered by the partial-failure tests in §8.3, which drive the
provider boundary with a stub.
