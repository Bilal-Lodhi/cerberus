# Cerberus v0.6.1 — Read-Path Measurement & Freshness Contract

**Published 2026-09-27 as a GitHub pre-release.** Annotated tag `v0.6.1`, tag object
`5a4e3191c0e38bbef17d86ec2bfe7b29bdf4bf75`, target
`42c0cc8c0deba2a853c9c6f3295c1ad843276610`. Nothing else was published: no npm package, no
container image and no hosted deployment, and nothing marked stable or latest.

This is an experimental research system. It is **not production ready**.

## The theme

**A published measurement was wrong, and the correction is the release.**

The previous cycle reported that the live session detail cost **3.49 ms p50** against `v0.4.0`'s
**0.09 ms** — a **38×** regression attributed to the durable read the `v0.5.0` cycle added. The
question this cycle set out to answer was whether a bounded cache could buy that back without
weakening the correctness `v0.5.0` established.

The answer is **no cache, and the premise was a measurement artifact.** Four findings, in the
order they arrived:

1. **The benchmark's persistence double was measuring itself.** It ignored the `eventsLimit` and
   `includeAssessments` arguments the API sends, so every ingest and every live-detail read
   carried up to 500 micro-event documents the real store never returns. Corrected, the live
   detail is **0.10 ms** in that harness, not 1.21 ms, and the `v0.4.0`-to-`main` comparison is
   **0.04 ms against 0.10 ms**.
2. **Measured against a real MongoDB** — the instrument the stubbed benchmark cannot be — the
   live detail is **1.36 ms p50 / 1.96 ms p95**, it makes **exactly one** persistence call per
   request, and it is **flat in the size of the store**, because it is a lookup on a unique index.
3. **The console does not poll the live detail.** It polls the *review* detail at 12
   requests/minute; the live detail is a fallback. The surface the cycle wanted to cache has zero
   steady-state traffic.
4. **The surface that does not scale is the live list**: `find({})` with no filter and no limit,
   **2.53 ms p50 at 20 stored sessions and 75.58 ms at 5 020**.

## Why this is `0.6.1` and not `0.7.0`

The cycle prepared a `v0.7.0` candidate and the maintainer decided against it. Nothing a client
can observe about the running system changed:

| | |
| --- | --- |
| Route behaviour | **Unchanged.** No route, no handler, no query |
| Response shape | **Unchanged.** No field added, none removed, none renamed |
| Server configuration | **Unchanged.** No new variable the API or the MCP adapter reads |
| Cache | **None introduced.** Every surface is `DURABLE_CURRENT` with a maximum staleness of **0 ms** |
| Schema, indexes, migrations | **Unchanged.** Migration `0004` is untouched; there is no `0005` |
| Paid routes | **Byte-for-byte `v0.6.0`.** The `Idempotency-Key` contract, the claim protocol, the pending lease and the stale reclaim are unchanged |
| Behavioural code change | **One, and it is a test** |

The substance is measurement, benchmark-fidelity correction, a polling audit, a normative
document and two release-tooling fixes. Under SemVer discipline that is a **patch**.

The `v0.7.0` candidate documents were converted into this release's material rather than left in
the tree. A candidate that was never published and will not be is not something a reader should
have to disambiguate from the release that shipped.

## What this release contains

**A real-MongoDB read-path benchmark.** `npm run bench:read-path`
(`scripts/bench/run-read-path-bench.mjs`) drives the compiled API against a real driver and a real
server — real migrations, real indexes, the real tool registry — and reports **persistence calls
per request** alongside latency, which is the number a cache would actually change. It **refuses
to run** without `CERBERUS_BENCH_MONGODB_URI` rather than falling back to a stub: a read-path
figure produced against an in-process double is not a read-path figure, and a silent fallback
would make the number it printed indistinguishable from a real one.

**A normative freshness contract.**
[live-read-freshness-policy.md](../development/live-read-freshness-policy.md) defines four terms —
`DURABLE_CURRENT`, `BOUNDED_STALE`, `PROCESS_LOCAL`, `ABSENT` — states the maximum staleness per
surface, names the six states that may never be served stale, says what may and may not be cached,
and specifies the eight-clause gate a future bounded cache would have to pass. It was written
**before** any implementation, deliberately: a cache designed first and documented afterwards
produces a policy that describes whatever the code happens to do.

**A corrected stubbed baseline.**
[performance-baseline.md](../development/performance-baseline.md) was re-measured after the double
was fixed. Its superseded figures and the reasoning drawn from them are kept rather than deleted,
because the error is the finding.

**A fidelity suite for the benchmark's double.** `apps/api/test/bench-double.test.ts` drives the
same call through the benchmark's double and through the real tool registry and asserts they
agree. Nine of its ten cases fail against the pre-fix double.

**A console polling audit.**
[console-polling-audit.md](../development/console-polling-audit.md) records what the console
actually calls, with `file:line` evidence.

**Four benchmark-only environment variables** — `CERBERUS_BENCH_MONGODB_URI`,
`CERBERUS_BENCH_SESSIONS`, `CERBERUS_BENCH_EVENTS`, `CERBERUS_BENCH_SAMPLES`. Read by
`scripts/bench/`, never by the API or the MCP adapter. No effect on a deployment.

## The one behavioural change

**A flaky integration test was fixed, and strengthened.** `terminate racing auto-lock: exactly one
applies` asserted `lock.status === 200` inside a `Promise.all` race while its own comment said
"whichever order they landed in". When the terminate landed first, the ingest was correctly
refused with `409 SESSION_TERMINATED` — and the test failed for a correct system. It now asserts
the invariant that holds under either interleaving: the durable status is `terminated`, both
statuses are `200` or `409`, and a `409` carries `SESSION_TERMINATED`. A second deterministic test
forces the interleaving that used to flake, so the behaviour is asserted rather than sampled.

That is a **test** change. It is the only behavioural difference between `v0.6.0` and this release.

## The freshness contract, in one table

| Surface | Source | Maximum staleness | Terminal-state behaviour | Outage behaviour |
| --- | --- | --- | --- | --- |
| Live list | `statusSource` per row, `reconciled` per page | **0 ms** — `DURABLE_CURRENT` | A durably `terminated` session is dropped in the same request | `reconciled: false`, every row `process-local`, `200` |
| Live detail | `statusSource`, `reconciled`, `source` | **0 ms** — `DURABLE_CURRENT` | `terminated` is read from the document; a cached `active` cannot survive it | `200` labelled `process-local` when this process holds the session; `503` `SESSION_STORE_UNAVAILABLE` when nothing does |
| Review list and detail | durable by construction | **0 ms** — `DURABLE_CURRENT` | Reports the durable status verbatim | `503`, never a `404` and never an empty page |
| Dashboard counters | inherited from the live list | **0 ms** | Inherited | Inherited |

## Known limitation, deliberately not fixed

`MongoStore.listSessions` issues `find({})` with no filter and no limit, so the live list reads
**every session document ever created** — including the terminated and long-expired ones the
reconciler then discards.

| Stored sessions | Live rows | Live list p50 | Live detail p50 |
| --- | --- | --- | --- |
| 20 | 20 | 2.53 ms | 1.45 ms |
| 520 | 120 | 10.21 ms | 1.17 ms |
| 5 020 | 1 020 | **75.58 ms** | **0.98 ms** |

The live detail is flat; the live list is linear in the store. A deployment with a few hundred
monitored sessions a day accumulates `active`-but-expired documents indefinitely, because expiry
is derived and never persisted.

**The bounded query is deferred, and the reason is correctness rather than effort.** The obvious
filter is not exactly equivalent to the reconciler's rule, and the difference is a session that
silently disappears from the live list:

- `normalizeStatus` maps **any** unrecognised status, and a missing one, onto `active`, so
  "monitored" is `$ne: "terminated"` — which is not an index-friendly predicate, and any
  conservative `$or` branch covering the legacy values forces the collection scan the change
  exists to remove;
- `isExpired` treats a missing or unparseable timestamp as **not expired**, deliberately, so a
  recency bound would exclude documents the current code lists.

The fix is a bounded query **plus** a normalisation migration that makes the vocabulary total,
with an index and an equivalence proof. Landing a partial bound would make a number smaller and
the read path less trustworthy, which is the trade this cycle exists to refuse.

## What this release does not claim

1. **The API did not get faster.** What changed is the *measurement* of it, and a published figure
   that was wrong.
2. **The live list's scaling is not fixed.** It is disclosed, measured, and designed for; the
   change is not made.
3. **There is no cache.** The contract that would govern one is normative; the decision not to
   build one is recorded with its evidence.
4. **The 38× figure did not represent a real MongoDB measurement.** It was the benchmark's own
   double. The authoritative read-path figures are the real-Mongo ones.
5. **No latency, throughput or availability guarantee.** The benchmark figures are from one
   machine, one loopback `mongod`, one process, with no reverse proxy and no concurrency beyond
   the measured knee.
6. **No compliance or auditability claim.** `DURABLE_CURRENT` means the value was read from the
   store in this request. It is not a statement that the store is authoritative for legal
   purposes.
7. **No multi-replica cache-coherence story**, because there is no cache to cohere. Cross-replica
   convergence is immediate *because* every read reconciles, and that property would be lost by a
   process-local cache without shared invalidation.
8. **No console fix.** The audit found no visibility guard, no in-flight guard, duplicate
   concurrent detail requests on session selection, and `stopStreaming` not awaiting cancellation.
   All are recorded; none is fixed here.
9. **Not production ready.** The repository remains experimental. No hosted deployment, no endpoint
   agent, no accounts, no RBAC, no tenancy, no npm or container publication.
10. **No distributed rate limiter, no incident identity, no notification outbox.** Per-process
    limiting and at-most-once-per-stored-`riskAssessmentId` notification are unchanged.

## Upgrade path

Nothing to do.

```bash
git fetch --tags
git checkout v0.6.1
npm ci
npm run build
npm test
```

No migration runs, no index is created, no configuration is required, and no response shape
changed. A deployment on `v0.6.0` can be rolled forward or back with no data consequences.
