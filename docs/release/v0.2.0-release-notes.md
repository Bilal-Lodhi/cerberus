# Cerberus v0.2.0 — Operational Durability Release

> **Status: published as a GitHub pre-release.** This is an experimental research
> system. It is **not production ready**, and it makes no guarantee that it will
> detect or prevent anything.
>
> No package or container image was published. Nothing was marked stable or latest.
> `v0.1.0` remains published and remains a pre-release, with its annotated tag
> untouched.

## Theme

`v0.1.0` was an experimental research prototype: it worked, and it did not survive
scrutiny about what happened when it restarted, when a dependency was down, or when
a client misbehaved. `v0.2.0` is about **operational durability** — the properties
an operator relies on rather than the features a demo shows.

The phase that produced it had a stated exit condition, and every part of it is met.
Where a property could not be delivered, the documentation says so rather than
implying otherwise; those statements are collected under
[What this release does not claim](#what-this-release-does-not-claim).

## Headline changes

### A restart no longer loses or corrupts state

The largest limitation in `v0.1.0`. Counters were written with `$set` from whatever
the process held in memory, so a restarted process — holding counters that started at
zero — **replaced** a session's lifetime totals with its own. Forty events and twenty
pastes came back as one and one.

- Counters are now **hydrated** from the durable document before any event is applied.
- The storage layer applies them with **`$max`**, so a durable total cannot regress
  even if a caller sends a lower value.
- Every in-memory session field is inventoried and classified by where its authority
  actually lives: [development/session-state-model.md](https://github.com/Bilal-Lodhi/cerberus/blob/v0.2.0/docs/development/session-state-model.md).

Verified across a real process restart: five events before, one after, durable
`eventCount` reads **6** with `tabSwitchCount` and `fullscreenExitCount` intact.
Before the fix the same sequence produced **1**.

### Retries are safe, including after a restart

Deduplication lived in a 128-entry ring in process memory, which is empty in a new
process — so a batch retried after a restart was stored twice and counted twice.

`micro_events` now carries a unique index on `(sessionId, eventId)`. Ingestion upserts
with `$setOnInsert`, the store reports which events were **newly inserted**, and only
those are applied to in-memory state.

Content deduplication is also now **scoped to content-bearing events**. It previously
applied to signal events too, so two keystrokes with the same inter-key delay were
treated as one and the second was silently dropped.

**This is retry idempotency, not replay protection.** The monitored client supplies
`eventId`, so a client that wants to re-send content sends a fresh one. The threat
model says so explicitly.

### A migration framework, and the migration that repairs `v0.1.0`

`v0.1.0` had no migration concept. That was fine until a change was not a pure
addition — and the unique identity index above is not: it **cannot be created** on a
database holding the duplicates the pre-fix ingestion path produced. Such a database
would fail to start with an opaque duplicate-key error.

- An ordered, append-only, idempotent runner that **fails before mutating**, records
  what it did in a `schema_migrations` ledger, and refuses a database carrying
  migrations the running build does not know about.
- `npm run migrate` and `npm run migrate:dry-run`.
- Migration `0001-dedupe-micro-event-identity` removes only copies that are otherwise
  **identical**, and refuses — having written nothing — when a pair's copies disagree,
  naming the pairs.

### Readiness is real, and liveness is honest

`/health` returned `healthy` unconditionally, so a deployment whose persistence layer
was down reported itself healthy and kept accepting telemetry it could not store.

| Endpoint | Question | Checks dependencies | Response |
| --- | --- | --- | --- |
| `GET /health` | Is the process able to answer HTTP? | **No** | Always `200` |
| `GET /ready` | Can this instance serve requests needing persistence? | **Yes** | `200` / `503` |

The distinction is not pedantry: a liveness probe that fails when MongoDB is down
makes an orchestrator restart a healthy process in a loop while the outage continues.

### Rate limiting on the expensive paths

In-process token buckets per route category, applied **after** authentication. The
AI-backed endpoints are tightest — every request there spends money — and
`CERBERUS_AI_REQUESTS_PER_MINUTE` is the one limit worth tuning.

Four properties are deliberate and documented: after auth, keyed by category rather
than caller, `X-Forwarded-For` never trusted, and per process.

### Credential rotation without a hard cutover

`CERBERUS_API_KEY_PREVIOUS` and `CERBERUS_MCP_TOKEN_PREVIOUS` accept the value being
retired alongside the current one. Both comparisons always run, so the response time
does not reveal which key matched, and neither key is ever logged.

## Also in this release

- **Corpus management in the console.** The reference corpus had no console surface
  at all, so populating it meant hand-writing `curl`. See
  [operations/corpus-management.md](https://github.com/Bilal-Lodhi/cerberus/blob/v0.2.0/docs/operations/corpus-management.md).
- **A performance baseline.** `npm run bench`, measured, with p50/p95/p99 per case.
  Its first headline finding was a benchmark artifact; the document records the
  correction rather than deleting it.
- **Bounded in-memory session state.** `session.events` and `session.keystrokeDeltas`
  grew for a session's whole lifetime. Both are now windows, and
  `computeKeystrokeMetrics` no longer spreads a large array into `Math.max`, which
  threw `RangeError` past roughly 100 000 entries.
- **Several `v0.1.0` correctness fixes** that a 319-test suite could not see, because
  the test doubles disagreed with the real store: the session review reported the
  **oldest** risk assessment as the final one, and `terminalContent` was empty after a
  restart. Both are fixed, and the doubles now match the store.

## Breaking changes and migration impact

Two changes could require action. Everything else is additive.

### 1. An event without `eventId` is rejected

`MicroEvent.eventId` was already required by the declared contract; the route simply
did not enforce it. It is now the durable idempotency key, so an event that cannot be
identified cannot be deduplicated, and the request is refused with
`400 MISSING_EVENT_ID`.

**Impact:** a client sending events without an `eventId` was already out of contract
and will now be told so. The bundled console always sends one.

### 2. The unique index needs a migration on existing data

A database that ran `v0.1.0`'s ingestion path may hold duplicate `micro_events`
documents. The unique index cannot be created over them, so migration
`0001-dedupe-micro-event-identity` must run — which it does automatically on connect.

If a duplicate pair's copies **disagree**, the migration refuses and names the pairs.
That needs an operator decision; the migration will never delete one version of a
disagreement. See [operations/upgrade.md](https://github.com/Bilal-Lodhi/cerberus/blob/v0.2.0/docs/operations/upgrade.md#when-a-migration-refuses-to-run).

**Impact:** an upgrade on a clean database is a no-op. On a database with duplicates
it removes exact copies and records how many. On a database with genuine conflicts it
stops and asks.

### 3. New response fields

`POST /api/v1/guardian/ingest` reports `acceptedCount` and `duplicateCount`.
`processedCount` keeps its meaning — the batch size. `fullscreenExitCount` is added to
two session-list responses. All additive.

### Not breaking

No route was removed or renamed, no MCP tool was removed, no collection was renamed,
and no persisted field changed type. `GET /health` keeps its response shape.

## Upgrade procedure

```bash
# 1. Back up, and verify the backup
npm run backup
ls -la ./backups/<timestamp>/cerberus/

# 2. Read the migration plan (changes nothing)
npm run migrate:dry-run

# 3. Apply, or just restart — the adapter migrates on connect
npm run migrate

# 4. Restart the MCP adapter first, then the API
# 5. Confirm
npm run migrate:dry-run     # expect every migration "applied"
curl -s http://localhost:8080/ready
```

Full procedure, including what to do when a migration refuses:
[operations/upgrade.md](https://github.com/Bilal-Lodhi/cerberus/blob/v0.2.0/docs/operations/upgrade.md).

## What this release does not claim

Stated plainly, because each of these is a reasonable assumption a reader could
otherwise make.

| Not claimed | Reality |
| --- | --- |
| Production readiness | A research platform with a single shared credential and no authorization. See the threat model. |
| Multi-user, RBAC or SSO | One key, one tenant, no roles. Every authenticated caller is "the operator". |
| Replay protection against a hostile client | Retry idempotency only; the client supplies the idempotency key. |
| DDoS defence | Rate limiting is a per-process backstop. Unauthenticated throttling is the proxy's job. |
| Point-in-time recovery | A `mongodump` snapshot. No oplog capture, no scheduling, no off-host storage, no encryption. |
| Endpoint-agent coverage | Deferred by owner decision. No keystroke capture outside the browser console, no screenshots, no filesystem scanning. |
| A central session transition path | Status can still diverge between the two in-memory maps and MongoDB. Recorded as open. |
| Partial-failure semantics | A session-changing operation whose persistence succeeds but whose cache update does not is not modelled. Recorded as open. |

The full list is in [development/maturity-plan.md](https://github.com/Bilal-Lodhi/cerberus/blob/v0.2.0/docs/development/maturity-plan.md)
and [security/threat-model.md](https://github.com/Bilal-Lodhi/cerberus/blob/v0.2.0/docs/security/threat-model.md).
