# Cerberus v0.5.0 — Multi-Writer Consistency & Trust Boundaries

**PREPARED, NOT PUBLISHED.** This is a release candidate description. No tag has been created, no
GitHub release exists, and no npm package or container image has been published. Publication is a
separate human decision — see [release-checklist.md](release-checklist.md) and
[v0.5.0-checklist.md](v0.5.0-checklist.md).

**Cerberus is an experimental research system and is not production ready.** Nothing in this
release changes that, and nothing here is marked stable or latest.

## The theme

The `v0.4.0` cycle made Cerberus **inspectable**. It never asked what happens when two API processes
serve the same session at once, because the system had only ever run as one.

This release is about **telling the truth when more than one process is running**. Every state path
was re-examined against one question:

> If process A and process B handle requests for the same session at the same time, does Cerberus
> still tell the truth?

The answer was **yes for transitions and no for reads**, and the reads were the work. The
architecture deliberately stayed Mongo-backed: every guarantee added here is a property of a single
document or index, so none of them needs a lock service, a message bus, a shared cache, or a replica
set.

## The observable changes

### Live reads reconcile against durable truth

- **`GET /api/v1/guardian/sessions`** issues **one batched durable query per request** — always, not
  only when its own memory is empty — and merges durable over local. A session another process
  terminated is dropped in the same request that would have reported it, and another process's
  sessions appear. The response gains `reconciled`; each row gains `statusSource` and
  `ephemeralStateAvailable`.
- **`GET /api/v1/guardian/sessions/:sessionId`** reads the session document on **every** request and
  merges the same way. The session object gains `statusSource` and `reconciled`.
- **When the store does not answer**, the page is still served, marked `reconciled: false`, with
  every row labelled `statusSource: "process-local"`. Refusing would take the live dashboard down
  during a store blip; presenting the local value as durable truth would be a lie.

### Two writers no longer lose data

- **Aggregate counters** are sent as a batch **delta** and applied with `$inc`. They were sent as
  absolute totals and applied with `$max`, so two processes accepting distinct events converged to
  the larger single process's total rather than the sum — a session with 10 events, 5 accepted by
  one process and 3 by another, read `15` instead of `18`. A deployment that has been running more
  than one replica may see a counter **increase**; that is the missing events being counted.
- **`terminalContent` has an owner**: the process whose terminal transition actually applied. A
  terminate that did not claim the session may only repair an empty field, so a stale replica cannot
  overwrite the workspace another replica preserved.

### Release and packaging hardening

- **`packages/mcp-mongodb` is `private`**, and `npm run verify:packages` makes every workspace
  package unpublishable by construction. It had shipped without the field through four releases.
- **The release-verification drill is reproducible in CI.** The workflow had never run; it now runs
  `npm run verify:release` on `workflow_dispatch` against a real `mongo:7`, with `contents: read`, no
  paid provider call, no repository secret, and an assertion that **no step was skipped**.

## Compatibility

**No field is removed or renamed, no status vocabulary changes, and no MCP tool is deprecated.** An
existing client needs no change: it sees more rows, a corrected counter and risk score, and new
fields it can ignore. The two MCP changes are additive — `update_session_counts` gains an optional
`countsDelta`, `update_session_terminal_content` gains optional `expectedStatuses` and
`onlyIfAbsent` and reports `updated`. With neither gate the behaviour is unchanged.

Three observable corrections, each to a statement that was false, and one correctness fix to a
durable value: the live list includes sessions this process did not deploy; a session another
process terminated stops appearing immediately on both live surfaces; `riskIndex`,
`overallRiskScore` and `peakRiskScore` are the reconciled maximum; and the counters rise by the
right amount. The full record is in [compatibility.md](../compatibility.md) §1b.

**No schema migration ships with this release.** No collection, field or index is added.

## What this release does not claim

1. **Not production ready.** Still an experimental research system.
2. **Not a distributed system.** No lock service, message bus, shared cache, or replica set. Where a
   single-document guarantee was insufficient, that is documented as a limitation rather than solved
   by adding a system.
3. **Not exactly-once billing.** The two paid routes are not idempotent; a retry after a lost
   response executes the provider call again, and `POST /scenarios` spends **twice** per request.
   Re-accepted with the cost measured, not fixed.
4. **Not per-user attribution, accounts, RBAC, or tenancy.** One shared operator key still grants
   equivalent authority to every replica.
5. **Not a global rate limit.** The limiter is per process and its ceiling multiplies by the replica
   count.
6. **Not deduplicated notifications.** Two replicas can each notify for one incident.
7. **Not a measured latency claim.** The reconciliation's query count is bounded and asserted; its
   wall-clock cost was not measured.
8. **Not a compliance claim.** The session model is an engineering property, not a control.
9. **No endpoint agent, and no new monitored data.** Telemetry still originates only from the browser
   console.
10. **Not a rewrite of published history.** The four published tags are unchanged, including the
    eleven historical synthetic co-author trailers.
