# Cerberus v0.6.0 — Durable Idempotency & Side-Effect Safety

**Prepared, not published.** This document describes a release candidate. Nothing has been
tagged, published, uploaded or deployed. Publication is a separate human decision, and
`docs/release/release-checklist.md` records what that decision involves.

Cerberus remains an **experimental research system**. It is not production ready, it makes no
compliance claim, it has no accounts or roles, it runs on one shared operator key, and it has no
endpoint agent. What follows is what changed, what it costs, and — plainly — what it does not
claim.

## The theme

The `v0.5.0` cycle made the system tell the truth when more than one API process serves the same
session. It left one boundary unresolved, and recorded it as a decision rather than a defect:

> What exactly happens when a caller retries a paid operation after an ambiguous response,
> especially when two API processes receive the same request at nearly the same time?

The honest answer was "the operation runs twice and you are charged twice, and the mechanism that
would fix it is designed but not built". This release builds it.

## What changed

### The two paid routes are retry-safe when a caller sends a key

`POST /api/v1/scenarios` and `POST /api/v1/auditor/query` accept an optional **`Idempotency-Key`**
request header. With one:

| Situation | Answer |
| --- | --- |
| same key, same request, first completed | the recorded status and body, `Idempotency-Replayed: true`, **no provider call** |
| same key, same request, first in progress | `409 IDEMPOTENCY_IN_PROGRESS` with `Retry-After`, **no provider call** |
| same key, different request | `409 IDEMPOTENCY_CONFLICT`, nothing spent |
| invalid key | `400 INVALID_IDEMPOTENCY_KEY`, **no claim written** |
| claim store unreachable | `503 IDEMPOTENCY_STATE_UNAVAILABLE`, **nothing claimed, nothing spent** |
| no key | exactly the behaviour of every earlier release |

The mutual exclusion is a **unique index** on `(routeFamily, sha256(key))` in a new
`operation_claims` collection. That is the whole of it: no lock service, no Redis, no replica
set, no transaction. Two API processes racing one key both attempt the insert, the index refuses
the second, and the loser reads the winner's record instead of calling the provider.

### The record, and what it deliberately does not hold

One document per attempt: the route family, `sha256(key)`, a canonical request fingerprint and
its version, the state, an ownership token, two deadlines, and the response to replay.

It holds **no prompt, no question, no provider message and no key**. The stored key form is a
digest, and a log line carries eight hex characters of that digest — enough to join two lines to
one operation, and a one-way derivation of a value the caller chose.

The fingerprint is a `sha256` over a canonical serialisation of the fields that decide what the
operation does, with object keys ordered **by UTF-16 code unit** rather than `localeCompare` — a
locale-sensitive order would make two replicas disagree about the digest of one request.

### Failure semantics that distinguish two kinds of failure

This is the part that matters most, and it is the part a marker alone would get wrong:

- **A provider outage, a refusal, or a cancellation** produced nothing usable, so a same-key
  retry **re-executes**. A transient outage does not poison a key until it expires.
- **A failure where Cerberus observed the provider succeed** and could not record the result is
  recorded **non-retryable** with the failure to replay. The money is already spent, so a
  same-key retry answers from the record instead of spending again — and a caller who wants a
  different outcome uses a new key, which is a deliberate act rather than a silent second charge.

### Retention, and the one setting

`CERBERUS_IDEMPOTENCY_TTL_SECONDS` (default 24 hours, bounded 60–604 800, validated fail-closed)
is the only new configuration. The **lease** — how long an in-progress claim blocks a retry — is
derived from `OPENAI_REQUEST_TIMEOUT_MS` rather than configured beside it, so a lease can never be
set shorter than a provider call. That misconfiguration would let a second process reclaim a
*healthy* operation and spend again; deriving it makes the state unrepresentable.

Retention is enforced by a MongoDB TTL index, which sweeps **approximately**. Nothing depends on
exact wall-clock expiry.

### One observable change, and it is a fix

A failed `list_sessions` on `POST /api/v1/auditor/query` used to be substituted with an empty
list, so the route summarised nothing and returned `200` with a plausible-looking answer — a
database outage presented as an audit finding. It now answers `503 AUDITOR_STORE_UNAVAILABLE`.

That was untruthful on its own. It became a **correctness** defect once the response started
being recorded for replay: a `200` recorded as completed would replay the fabricated answer for
the whole retention window. A response is only worth remembering if it is true.

### One duplicate notification is gone, and one is re-accepted

`store_risk_assessment` carries a unique index on `riskAssessmentId`, so a second write of one id
reports `inserted: false`. The route read only `stored.ok` and **discarded `inserted`**, so a
second analysis producing an id already in the database locked the session and sent a second
alert. It now suppresses the alert. That is a durable, atomic, cross-replica dedupe that needed
**no new collection, index or migration**.

What remains: two API processes analysing one session concurrently mint **different**
assessment ids, because the id is model-supplied rather than derived from the incident. A marker
cannot fix that — it would need a durable *incident* identity, which does not exist, and a marker
on an unstable key would trade a duplicate alert for a **lost** one. No outbox is built, and the
reason is recorded rather than implied.

### Measured: what the previous release's correctness cost

`v0.4.0` against this release, same benchmark code, same machine, back to back:

| Case | before p50 | after p50 | delta |
| --- | --- | --- | --- |
| `GET /guardian/sessions` (live list) | 2.93 ms | 3.39 ms | +16 % |
| `GET /guardian/sessions/:id` (live detail) | 0.09 ms | 3.49 ms | **+3 588 %** |
| every other case | — | — | inside run-to-run noise |

The live detail went from answering out of process memory to reading the durable session document
on every request. **That is the price of the correctness `v0.5.0` bought**: the old number was fast
because a session another replica had terminated was reported `active`.

Two things make the ratio unsurprising. The old denominator is near zero, so any work at all
produces a large ratio. And the benchmark runs in-process with the persistence adapter stubbed, so
the 3.4 ms is the route's own work — against a real MongoDB the absolute figure would be dominated
by the round trip and the ratio would be smaller.

### The benchmark itself had been broken since `v0.4.0`

Running it to produce the "before" number surfaced this: `npm run bench` — the command the
performance baseline calls the reproducible way to produce the baseline — threw before a single
case ran, because its config literal never gained the `log` field the application reads
unconditionally. Four releases, and nothing noticed. A test now asserts that literal covers every
key the application's config has, in both directions.

## Upgrade

**One migration**, `0004-paid-operation-claim-indexes`. It creates the new collection's two
indexes and **rewrites no data** — the collection is new, so there is nothing to repair and no way
for it to refuse, which is what makes it safe on a `v0.5.0` database of any size.

The documented procedure is unchanged: back up, read the plan with `npm run migrate:dry-run`,
apply, restart, confirm. See [operations/upgrade.md](../operations/upgrade.md).

**Nothing is required of an existing client.** The header is optional; a caller that sends none
gets exactly the behaviour it had. The one exception is the auditor's store-outage case above,
which now answers `503` instead of a fabricated `200`.

`docs/compatibility.md` §1c lists every observable change.

## What this release does **not** claim

1. **Not exactly-once billing.** The provider client retries internally, and a process that dies
   between the provider's response and the record write leaves an operation whose outcome is
   unknown. A retry after the lease expires may spend again. That window is stated in
   [development/paid-operation-state-model.md](../development/paid-operation-state-model.md) §11,
   and the residual case where the store refuses the failure write too is asserted by a test.
2. **Not exactly-once external side effects.** The scenarios matrix is persisted best-effort; a
   completed replay does not re-persist it, so a replay can answer with a matrix whose document
   was never written. That was already true of the first response.
3. **Not perfect replay protection, and not authorization.** A caller that sends a new key gets a
   new operation. The key grants no authority the shared operator key did not already grant.
4. **Not permanent.** A claim expires after the retention window; a retry after that is a new
   operation.
5. **Not clock-skew-proof.** The lease is evaluated against the claiming process's clock. The
   derived lease makes the window a fraction of a provider call rather than a fixed guess.
6. **Not exact TTL expiry.** MongoDB's TTL monitor is approximate.
7. **Not duplicate-free notifications.** An alert is at-most-once per stored assessment; two
   replicas analysing one session concurrently can still alert twice. No outbox exists.
8. **Not production ready.** No accounts, roles, tenancy or per-user attribution; one shared
   operator key; no hosted deployment; no npm package; no container image.
9. **Not a compliance control.** A risk score is a signal for a human reviewer, never a finding
   of intent.
10. **Not a fix for the 38× live-detail cost.** It is measured and published, not removed. A
   deployment that cannot afford a durable read per live-detail request has a real trade to make,
   and this release gives it the number rather than a promise.
