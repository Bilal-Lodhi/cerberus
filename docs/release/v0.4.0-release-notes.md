# Cerberus v0.4.0 — Operability & Read Integrity

**Status: release candidate. Prepared, not published.** No tag, no GitHub release, no
package, no container image and no deployment exists for `0.4.0`. The version in
`package.json` is still `0.3.0`, because the bump is part of publication and publication is
not authorised. See [v0.4.0-checklist.md](v0.4.0-checklist.md) for the gates and what
publishing would still require.

Cerberus is an experimental research system and is **not production ready**. This release
does not change that, and nothing in it should be read as a compliance or audit-trail
claim.

## The theme

**Operability and read integrity.** The `v0.3.0` cycle made the system architecturally
coherent: one canonical transition boundary, explicit partial-failure semantics,
deterministic behaviour under retry and restart. What it could not do was be *inspected*.

A request could not be traced: `docs/api-errors.md` promised that an error body's
`correlationId` matched the `X-Correlation-Id` response header and the server log line, and
that was false for four of the five route groups — each minted its own `randomUUID()` per
handler, and outside development mode there was no request log line at all.

A session detail answered `404` for a session that existed, immediately after a restart.

A partial deletion was reported as a complete one, and the session record was removed
*first* — so a failure orphaned the telemetry that record was the only way to find.

And the release gates lived in a session: a sequence of commands run by hand, with one of
them verified against a **stale container image** because nothing compared what the image
was built from against the source it was supposed to be built from.

This release closes those, and makes every release-critical check one command that can be
run again by anyone.

## What is observably different

### Structured logs, and one request id

`CERBERUS_LOG_LEVEL` (`debug`/`info`/`warn`/`error`, default `info`) and
`CERBERUS_LOG_FORMAT` (`pretty`/`json`, default `pretty`). An unusable value is a startup
error rather than a silent fallback.

One line per HTTP request, emitted after the response exists, carrying the status, the
latency, the **matched route template** — never the concrete path, because a session id is
not a route — and the stable error code. Per-step detail for MCP calls and provider
attempts at `debug`.

Every request gets exactly one identifier: generated when absent, accepted from
`X-Request-Id` only when it is at most 128 characters and uses `A-Z a-z 0-9 . _ : -`,
echoed in both `X-Request-Id` and `X-Correlation-Id`, recorded on the request line, and
returned in every error body's `correlationId`. A rejected identifier is replaced, not
rejected — which is why there is no `INVALID_REQUEST_ID` code.

**Secrets cannot reach a log line.** Every configured secret is registered with the
redactor at startup, and credential-shaped content is scrubbed by pattern. A monitored
workspace, a paste, a telemetry batch or a provider prompt is withheld wholesale rather
than masked. Asserted by a sweep that drives real requests at `debug`.

### The read model

`GET /api/v1/guardian/sessions/:id` reads `sessionStore` (no persistence call), then the
durable document, then the live registry — and reports which answered through `source` and
`ephemeralStateAvailable`. Immediately after a restart it answers for a session that exists
durably, with no recovery step first.

All four surfaces that answer for a session now report **one lifecycle vocabulary**. The
derived review value moved to a new `disposition` field, because folding it into `status`
made the review detail the only surface reporting `flagged` where the review *list*
reported `active` — and the console displayed such a session as LOCKED while the dashboard
displayed it as active.

### Exact deletion reporting

A deletion cascades over three domain components — `session`, `telemetry`, `assessments` —
and the response names what was removed and what was not, on success and on failure alike.
A partial deletion is `500 PARTIAL_DELETE` with `retrySafe: true`, deliberately distinct
from `503 SESSION_STORE_UNAVAILABLE`, which means nothing was attempted. The store removes
the derived documents first and the session record **last**, so a partial failure leaves
the session identifiable and the operation retryable, and nothing is orphaned.

### One status vocabulary

`cleared` is gone. It had no producer at all: nothing wrote it, `set_session_status` never
accepted it, and the product's one "clear" behaviour — lifting a lock when the score falls
— writes `active`. So the historical meaning of `cleared` **is** `active`. It was not given
a producer, because doing that would mean inventing a human review workflow to justify an
enum.

`flagged` and `investigating` left the vocabulary at the same time, for the same reason:
they are a disposition, not a lifecycle state. A document still holding any of the three
normalises to `active` on read and is **repaired** on its next transition — logged as
`session.transition.repaired`, because silently rewriting a stored field is worth knowing
about.

### Repeatable release gates

`npm run verify:release` runs sixteen checks in one command and reports each one's outcome:
build, typecheck, the test tree's typecheck, the unit suites, the same suites against a real
MongoDB, the upgrade gate, the docs checker, the version census, the configuration census,
the secret guards, the backup/restore drill, the stale-image defence, and the Flutter
format/analyze/test trio.

**It cannot publish.** `secret-guards` fails if a publishing command appears anywhere under
`scripts/release/`.

A skip is not a pass: a step whose precondition is absent is skipped with the reason printed
and counted separately.

Four gates are worth naming:

- **The upgrade gate** takes a database as a published release left it and walks dry run,
  migrate, validate, re-run against a real MongoDB. The historical shape of `v0.2.0` and
  `v0.3.0` is described once, derived from the release notes rather than from the code, so
  it cannot drift from the state it claims to represent.
- **The backup/restore drill** creates its own disposable database, seeds a fixture with an
  empty collection and the critical indexes, and verifies the whole procedure — including
  that a restore preserves the uniqueness guarantees, which a count comparison cannot see.
- **The stale-image defence** builds the image `--no-cache`, tags it uniquely per run, and
  compares its recorded version and commit with the working tree and with the running
  container.
- **The browser smoke** drives the built console in headless Chrome and asserts that it
  renders, that the console reports no error, and that nothing overflows.

## Upgrade path

**No schema migration ships with this release.** No new migration, no field rename, no
collection change. `npm run migrate` applies nothing.

**No data migration is required.** A document holding a retired status value is normalised
on read and repaired on its next transition.

**Four client-visible changes**, recorded in
[docs/compatibility.md](../compatibility.md) §3.1:

1. `SessionReviewResponse.status` is the lifecycle status on every surface; the derived
   value is `disposition`. A client that branched on `status` for `flagged` must read
   `disposition`.
2. `correlationId` now matches the response headers on every route, and `X-Request-Id` is
   accepted and echoed. A client may send one; an invalid one is replaced.
3. `cleared` is removed from the vocabulary.
4. `PARTIAL_DELETE` and `REFERENCE_NOT_FOUND` are new codes; `SESSION_NOT_FOUND` is
   returned by every surface that can report it; a session detail can answer
   `SESSION_STORE_UNAVAILABLE` for a read.

Upgrading is: stop the API, deploy the new build, start it. Migrations run automatically on
connect, and there are none to run. See
[docs/operations/upgrade.md](../operations/upgrade.md).

## What this release does not claim

1. **Not production ready.** No guarantee of detection or prevention.
2. **No endpoint agent.** Telemetry comes from the browser console.
3. **No hosted deployment, no accounts, no RBAC, no tenancy.** A single shared operator key,
   and the console embeds it in the built bundle.
4. **No npm package and no container image were published.** The repository is the artefact.
5. **Rate limiting is a per-process backstop.** N replicas enforce up to N times the limit.
6. **The two paid routes remain non-idempotent.** A retry after a lost response re-spends.
7. **Backups have no scheduling, off-host storage, encryption or point-in-time recovery.**
   The drill verifies the procedure, not the policy.
8. **The live surfaces report the status this process holds in memory.** A status changed
   durably by another writer is visible on the review surface immediately and on the live
   surfaces once a transition reconciles the cache.
9. **The terminology pass in the browser smoke is a human reading screenshots.** Flutter web
   renders into a canvas; the machine-verifiable half is the widget suite.
10. **Structured logs are not a compliance claim.** Cerberus writes to `stdout` and `stderr`
    and ships, stores, rotates and expires nothing. Retention, access control and the legal
    basis for keeping request metadata are the deployer's.
