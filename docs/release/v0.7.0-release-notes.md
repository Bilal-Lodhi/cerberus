# v0.7.0 release notes — **candidate, not published**

> **Nothing here has been published.** There is no `v0.7.0` tag, no GitHub release, no npm package,
> no container image and no deployment. This document describes a release candidate so that the
> decision to publish it can be made against something written down, which is the same discipline
> `v0.6.1`'s candidate followed. `v0.1.0`–`v0.6.1` are unchanged and immutable.

**Theme: Bounded Live Sessions & Storage Normalisation.**

The live session list stops reading the whole session collection. It is answered by a bounded,
index-backed durable query whose result is proven equal to the previous build's full scan — field
for field, in order — for every document the previous build could see, including legacy, hand-edited
and malformed ones. A migration normalises the two stored fields that makes possible.

The list's p50 is **flat from 20 to 20 020 stored sessions** where it used to grow linearly: the
point that cost **75.58 ms** at 5 020 stored sessions now costs **3.45 ms**, and the query examines
**20 documents** at every size instead of every document ever written.

## Why a minor version, if it is published

`0.7.0`, not `0.6.2`. Two things a deployment must do or know change:

- **A schema migration ships**, and it rewrites documents: `monitored_sessions.status` is normalised
  and `monitored_sessions.liveListUpdatedAt` is derived. An upgrade from `v0.6.1` has one migration
  to apply, and an operator who inspects a database between the migration and the service restart
  sees documents that the previous build would not have written.
- **Two indexes are added** to `monitored_sessions`, which a restore must now preserve and a
  capacity plan must account for.

The **API contract does not break**: no route changed, no response field was added or removed, no
error code changed, no configuration was added, and no cache was introduced. Every read surface is
still `DURABLE_CURRENT` with **0 ms** maximum staleness. Under SemVer, a storage-behaviour and
upgrade-requirement change is a minor version; under this repository's own policy it is recorded in
[../compatibility.md](../compatibility.md) §1d.

## Added

- **A bounded live-list query.** `GET /api/v1/guardian/sessions` reads the documents that can appear
  on the page, from two indexes, instead of every session document ever created. One durable query
  per page, unchanged; `persistence calls per request` stays at **1.00**.
- **Migration `0005-normalise-session-list-fields`.** It writes `status` as the value the API was
  already computing from it, and derives `liveListUpdatedAt` from `updatedAt`, `deployedAt` or
  `createdAt`. It deletes nothing, rewrites no other field, and never reads the clock.
- **Two indexes**: `live_list_status_updated_at` (`{ status: 1, updatedAt: -1 }`) and
  `live_list_status_liveness` (`{ status: 1, liveListUpdatedAt: -1 }`).
- **An optional `liveList` argument on the `list_sessions` MCP tool.** Omitted, the tool returns
  exactly what it returned before.
- **A third category in the critical-index list**, `queryIndexes`, verified after every restore by
  name — a bounded read's index fails differently from a uniqueness guarantee: losing it changes no
  answer, it makes the read unbounded again.
- **Two release-harness steps**: `verify:live-list` (the seven live-list suites) and
  `verify:live-list-bench` (the deterministic part of the benchmark — the previous query must
  collect-scan, the bounded one must not, and the cost must not follow the collection).

## Changed

- **`monitored_sessions.status` is normalised** for documents whose stored value was missing,
  `null`, unknown, a case variant or of another type. Every value written is the value
  `normalizeStatus` was already computing, so no surface reports a different status — but a
  compare-and-set on `expectedStatuses` now matches a document whose stored status was, say,
  `"cleared"`, which is a repair rather than a new behaviour.
- **The order of live-list rows that share a `deployedAt` to the millisecond is now `sessionId`
  ascending.** That order was previously whatever MongoDB returned, which no client could rely on.
  No pair with different `deployedAt` values moves.
- **`monitored_sessions` gains the stored `liveListUpdatedAt` field.** It is a predicate field: the
  live list does not project it, so no response gained a field. It is visible in the review detail's
  session document, which returns the stored document.

## The equivalence, and why it is the substance of the release

The speed is a consequence. The invariant is the release, and it is proven rather than asserted:

- the current semantics are written down first, case by case, in
  [../development/live-list-equivalence-model.md](../development/live-list-equivalence-model.md) —
  including that only the exact string `terminated` is terminal, that an unreadable timestamp means
  *not expired*, and that the reconciler evaluates expiry through two branches that consult
  different fields;
- migration `0005` is **reconciler-neutral**: it rewrites a status into the value the reconciler was
  already computing and adds a field the reconciler never reads;
- the bounded query is **complete** — it returns a superset of what the reconciler needs, and
  over-selecting is harmless because the reconciler drops what is not live;
- the end-to-end comparison is one reconciler over two document sets, on a 41-row adversarial
  fixture and on sixty generated fixtures, comparing every field of every row in order;
- the mirror of the query used by the property test is **grounded against a real server**;
- a query-plan gate asserts the server uses a **named** index, with a negative control that proves
  the instrument can see a collection scan at all.

Three published predictions were corrected in the process, and the corrections are recorded rather
than quietly dropped: `$ne: "terminated"` **is** index-friendly; rewriting `updatedAt` in place
would have **changed an answer** for malformed documents; and one index was not enough. See
[../development/bounded-live-list-checkpoint.md](../development/bounded-live-list-checkpoint.md) §3.

## Upgrade path

```bash
git fetch --tags
git checkout <the published tag>
npm ci
npm run build
npm run migrate:dry-run     # see exactly what 0005 would change, and change nothing
npm run migrate             # or just restart: connect() applies it before it serves
npm test
```

Nothing to configure. The migration is idempotent, cannot refuse, deletes nothing and never reads
the clock. **Run it before the new build serves** — `connect()` does that for you — and read
[../operations/upgrade.md](../operations/upgrade.md) for the rolling-upgrade ordering as a table,
the dry run's accounting, and the rule for editing a session document by hand.

A downgrade means restoring a backup taken before the upgrade. There is no down-migration, and a
restored database is verified against the critical-index list, which now includes the two live-list
indexes.

## Known limitations, carried or introduced

1. **One document shape is invisible to the bounded query.** A document the migration has *not*
   classified whose `updatedAt` is not a `Date`. No version of the store can produce it — every
   write path sets a `Date` `updatedAt`, and `connect()` migrates before it serves — so reaching it
   means hand-editing a document after the migration. Writing the document closes it.
2. **A direct database edit must keep the normal form.** A status outside
   `active | locked | terminated`, or a document with no `liveListUpdatedAt` and no `Date`
   `updatedAt`, can hide a session from the live list until it is written again.
3. **The unbounded read is still reachable**, deliberately: a process started with `migrate: false`
   against a database with pending migrations reads the collection exactly as the previous build
   did, and warns once. Correctness never depends on having migrated; only cost does.
4. **The `updatedAt` reader asymmetry is retained**, now with the proof that closing it would change
   an answer.
5. **The console's polling defects are unchanged** — no visibility guard, no in-flight guard,
   duplicate detail requests on selection, `stopStreaming` not awaiting cancellation.
6. **No cache, no endpoint agent, no accounts, no RBAC, no tenancy, no incident identity, no
   notification outbox, no distributed rate limiter, no new AI provider.**

## What this release does not claim

1. **No latency, throughput or availability guarantee.** The figures are one machine, one loopback
   `mongod`, one process, single runs, no reverse proxy.
2. **No cache**, so every read surface remains `DURABLE_CURRENT` with 0 ms maximum staleness.
3. **No compliance or auditability claim.** `DURABLE_CURRENT` means the value was read from the
   store in this request.
4. **Not production ready.** The repository remains experimental: no hosted deployment, no endpoint
   agent, no accounts, no RBAC, no tenancy, no npm or container publication.
5. **No multi-replica cache-coherence story**, because there is no cache to cohere.
