# Cerberus v0.7.0 — Freshness Contracts & Read-Path Efficiency

**Prepared, not published.** This document is the release candidate's notes. Nothing has been
tagged, pushed as a release, packaged or deployed.

## The theme

**Cerberus now states what "current" means, per surface, in one normative document — and the
measurement that decided whether to trade any of it away turned out to be wrong.**

The cycle began from a published number: the live session detail cost **3.49 ms p50** against
`v0.4.0`'s **0.09 ms**, a **38×** regression attributed to the durable read the `v0.5.0` cycle
added. The question was whether a bounded cache could buy that back without weakening the
correctness `v0.5.0` established.

The answer is **no cache, and the premise was a measurement artifact.** Three findings, in the
order they arrived:

1. **The benchmark's persistence double was measuring itself.** It ignored the `eventsLimit` and
   `includeAssessments` arguments the API sends, so every ingest and live-detail read carried up
   to 500 micro-event documents the real store never returns. Corrected, the live detail is
   **0.10 ms** in that harness, not 1.21 ms, and the `v0.4.0`-to-`main` comparison is **0.04 ms
   against 0.10 ms**.
2. **Measured against a real MongoDB** — the instrument the stubbed benchmark cannot be — the
   live detail is **1.36 ms p50 / 1.96 ms p95**, it makes **exactly one** persistence call per
   request, and it is **flat in the size of the store** because it is a lookup on a unique index.
3. **The console does not poll the live detail.** It polls the *review* detail at 12
   requests/minute; the live detail is a fallback. The surface the cycle wanted to cache has zero
   steady-state traffic.

## What this release contains

**A normative freshness contract.** [live-read-freshness-policy.md](../development/live-read-freshness-policy.md)
defines four terms — `DURABLE_CURRENT`, `BOUNDED_STALE`, `PROCESS_LOCAL`, `ABSENT` — states the
maximum staleness per surface, names the six states that may never be served stale, says what may
and may not be cached, and specifies the eight-clause gate a future bounded cache would have to
pass. It was written **before** any implementation, deliberately: a cache designed first and
documented afterwards produces a policy that describes whatever the code happens to do.

**A real-MongoDB read-path benchmark.** `npm run bench:read-path` measures the live and review
read surfaces against a real driver and a real server, and reports **persistence calls per
request** alongside latency — the number a cache would actually change. It **refuses to run**
without `CERBERUS_BENCH_MONGODB_URI` rather than falling back to a stub. The baseline is in
[read-path-performance.md](../development/read-path-performance.md).

**A corrected stubbed baseline.** [performance-baseline.md](../development/performance-baseline.md)
was re-measured after the double was fixed. Its superseded figures and the reasoning drawn from
them are kept rather than deleted, because the error is the finding.

**A fidelity suite for the benchmark's double.** `apps/api/test/bench-double.test.ts` drives the
same call through the benchmark's double and through the real tool registry and asserts they
agree. Nine of its ten cases fail against the pre-fix double.

**A console polling audit.** [console-polling-audit.md](../development/console-polling-audit.md)
records what the console actually calls, with `file:line` evidence.

## The one observable behaviour change

**A flaky integration test was fixed, and strengthened.** `terminate racing auto-lock: exactly one
applies` asserted `lock.status === 200` inside a `Promise.all` race while its own comment said
"whichever order they landed in". When the terminate landed first, the ingest was correctly
refused with `409 SESSION_TERMINATED`. The test now asserts the invariant that holds under either
interleaving — the durable status is `terminated`, both statuses are `200` or `409`, and a `409`
carries `SESSION_TERMINATED` — and a second deterministic test forces the interleaving that used
to fail.

That is a **test** change. It is the only behavioural difference between `v0.6.0` and this
candidate.

## What did not change

- **No route, no query, no configuration and no response field.** `statusSource`, `reconciled`,
  `source` and `ephemeralStateAvailable` are unchanged, and no field was removed.
- **No cache, and no staleness.** Every surface remains `DURABLE_CURRENT`: the value was
  reconciled against the durable store during the request.
- **No schema change, no migration, no new index.** Migration 0004 and the `operation_claims`
  collection are untouched.
- **No paid-route change.** The `Idempotency-Key` contract, the claim protocol, the pending lease
  and the stale reclaim are exactly as `v0.6.0` shipped them.

## What this release does not claim

1. **Not a performance release.** The API did not get faster. What changed is the *measurement* of
   it, and a published figure that was wrong.
2. **Not a cache release.** No cache was built. The contract that would govern one exists and is
   normative; the decision not to build one is recorded with its evidence.
3. **Not a solution to the live list's scaling.** `MongoStore.listSessions` is still `find({})`
   with no filter and no limit, so the live list is linear in the number of stored sessions
   (2.53 ms at 20, **75.58 ms** at 5 020). The design is written down; the change is not made.
4. **Not a compliance or auditability claim.** `DURABLE_CURRENT` means the value was read from the
   store in this request. It is not a statement that the store is authoritative for legal
   purposes.
5. **Not a multi-replica cache-coherence story**, because there is no cache to cohere. Cross-replica
   convergence is immediate *because* every read reconciles, and that property would be lost by a
   process-local cache without shared invalidation.
6. **Not a console fix.** The audit found no visibility guard, no in-flight guard, duplicate
   concurrent detail requests on session selection, and `stopStreaming` not awaiting cancellation.
   All are recorded; none is fixed here.
7. **Not a production-ready claim.** The repository remains experimental. No hosted deployment, no
   endpoint agent, no accounts, no RBAC, no tenancy, no npm or container publication.
8. **Not a distributed rate limiter.** Per-process limiting is unchanged.
9. **Not an incident-identity or notification-outbox change.** Duplicate notifications across
   distinct model-supplied `riskAssessmentIds` remain possible.
10. **Not a paid-AI claim.** No paid provider call is made by any test, benchmark or CI job in this
    repository.

## The case for `v0.6.1` instead

The only behavioural change is to a test. Everything else is documentation, measurement and a
benchmark harness. A reviewer could reasonably call this `v0.6.1` — a patch that corrects a
published figure and a flaky gate.

The argument for `v0.7.0` is that the release **adds a normative document that constrains future
work**: the freshness contract, the per-surface staleness statement, and the eight-clause gate a
cache must pass. That is a contract surface, not a patch, and a reader who pins `0.6.x` should
know that "what does current mean" now has a written answer.

**Recommendation: `v0.7.0`.** The decision is the maintainer's and is recorded as such.

## Upgrade path

Nothing to do.

```bash
git fetch --tags
git checkout v0.7.0        # after publication
npm ci
npm run build
npm test
```

No migration runs, no index is created, no configuration is required, and no response shape
changed. A deployment on `v0.6.0` can be rolled forward or back with no data consequences.
