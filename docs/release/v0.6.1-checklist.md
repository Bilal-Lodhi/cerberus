### The harness was run in the shape CI does not, and that found a defect

The same harness was run through the `Release verification` **`workflow_dispatch`** — the manual
drill, rather than a pull-request job. In the previous cycle's first run it came back **18 passed,
1 failed**: the attribution guard.

The guard's default range was the literal `origin/main..HEAD`. That is true in a developer's clone
and true in `ci.yml`, which passes an explicit `--range` derived from the event, and **false** in
this workflow, whose `actions/checkout@v4` fetched one ref and no remote-tracking branches.
`git log origin/main..HEAD` exited 128 and the guard died with an unhandled `execFileSync` stack
trace. Only the manual drill ran in the shape that exposed it.

Both halves were fixed and re-run:

| | |
| --- | --- |
| The guard | Tries `origin/main`, then `main`, then `refs/remotes/origin/HEAD`, and exits non-zero with a **diagnosis** when none resolves. An unresolvable base is not "nothing to check": a guard that examined no commits would report OK, which is the one answer it must never give for a range it could not read |
| The workflow | `fetch-depth: 0`, so what the guard resolves is the whole range being released rather than the tip alone |
| The test | `apps/api/test/release/attribution-guard-range.test.ts` drives the guard as a process and asserts the exit code, the diagnosis and that the base is discovered. Verified against a faithful reproduction of the `actions/checkout` shape — `git init`, `remote add`, `fetch --depth=1 <sha>`, `checkout FETCH_HEAD`, no refs at all — where the guard now exits 1 naming the fix |

## 6. Real-MongoDB read-path benchmark

`npm run bench:read-path`, against a loopback `mongo:7.0.43` container, on the verified candidate.
Two runs were taken because the machine's run-to-run spread is larger than several of the
differences between cases; the second is quoted, and the spread is stated rather than smoothed.

| Case | n | p50 | p95 | p99 | persistence calls/request |
| --- | --- | --- | --- | --- | --- |
| Live detail — this process holds the session | 300 | 1.37 ms | 2.22 ms | 2.66 ms | **1.00** |
| Live detail — after restart (memory empty) | 300 | 1.21 ms | 2.04 ms | 2.44 ms | **1.00** |
| Live list — 20 sessions | 150 | 1.67 ms | 2.24 ms | 2.64 ms | **1.00** |
| Review detail — durable evidence | 150 | 7.58 ms | 12.05 ms | 16.11 ms | **1.00** |
| Live detail — missing session | 300 | 1.33 ms | 1.92 ms | 2.26 ms | 1.00 (404 ×300) |
| Live detail — terminated session | 300 | 1.12 ms | 1.43 ms | 1.63 ms | 1.00 (200 ×300) |

Scaling, from the same run:

| Stored sessions | Live rows | Live list p50 | Live list p95 | Live detail p50 |
| --- | --- | --- | --- | --- |
| 20 | 20 | 1.61 ms | 2.12 ms | 1.09 ms |
| 520 | 120 | 10.32 ms | 14.37 ms | 1.16 ms |
| 5 020 | 1 020 | **96.76 ms** | 124.79 ms | **1.15 ms** |

Concurrency: 689 req/s at 1 in flight, 1 399 at 8, 1 375 at 32 for the live list; the live detail
reaches **2 361** at 8. Store unavailable: `200` labelled `process-local`, `503`
`SESSION_STORE_UNAVAILABLE`, list `reconciled: false` — every status the contract requires.

### No unexplained regression, and one number that had to be checked

The **first** run reported the live list at 20 sessions as **3.35 ms p50**, against a recorded
baseline of 1.59 ms — a 2× movement, which is the shape that should block a release. It was
checked rather than assumed:

- the **same run**, in its own scaling section, measured the identical workload — 20 stored
  sessions, 20 live rows, the same process — at **1.63 ms**;
- the second run measured it at **1.67 ms**.

So the 3.35 ms was machine noise, and the same-process pair (3.35 against 1.63 ms for one
workload) bounds the spread at roughly 2× on this machine. That is consistent with every earlier
figure in [read-path-performance.md](../development/read-path-performance.md), where this case has
read 1.53, 1.59, 2.16, 2.41 and 3.35 ms across runs.

**Every case is at or near the recorded baseline once the spread is accounted for**, and the
scaling shape is unchanged: the live detail is flat (1.09 → 1.15 ms across a 250× larger store)
and the live list is linear (1.61 → 96.76 ms). No regression is unexplained.

## 13. Worktree safety

No worktree was created for this release. The repository has exactly one worktree, and the
`v0.4.0` worktree used in the previous cycle was removed.

The unsafe pattern is recorded in [maturity-plan.md](../development/maturity-plan.md): a worktree
whose `node_modules` is a **Windows junction** must never be removed recursively, because removal
follows the junction — and then npm's own workspace junctions inside it, which point at
`apps/api` and `packages/mcp-mongodb` — and deletes both source trees. The two `node_modules/@cerberus/*`
junctions that exist are npm's own workspace links, not a shared-worktree setup.
