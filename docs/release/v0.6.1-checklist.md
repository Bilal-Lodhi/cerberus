### The harness was run in the shape CI does not, and that found a defect

The same harness was run through the `Release verification` **`workflow_dispatch`** — the manual
drill, rather than a pull-request job. In the previous cycle's first run it came back **18 passed,
1 failed**: the attribution guard.

The guard's default range was the literal `origin/main..HEAD`. That is true in a developer's clone
and true in `ci.yml`, which passes an explicit `--range` derived from the event, and **false** in
this workflow, whose `actions/checkout@v4` fetched one ref and no remote-tracking branches.
`git log origin/main..HEAD` exited 128 and the guard died with an unhandled `execFileSync` stack
trace. Only the manual drill ran in the shape that exposed it.

Both halves were fixed and re-run:

| | |
| --- | --- |
| The guard | Tries `origin/main`, then `main`, then `refs/remotes/origin/HEAD`, and exits non-zero with a **diagnosis** when none resolves. An unresolvable base is not "nothing to check": a guard that examined no commits would report OK, which is the one answer it must never give for a range it could not read |
| The workflow | `fetch-depth: 0`, so what the guard resolves is the whole range being released rather than the tip alone |
| The test | `apps/api/test/release/attribution-guard-range.test.ts` drives the guard as a process and asserts the exit code, the diagnosis and that the base is discovered. Verified against a faithful reproduction of the `actions/checkout` shape — `git init`, `remote add`, `fetch --depth=1 <sha>`, `checkout FETCH_HEAD`, no refs at all — where the guard now exits 1 naming the fix |

## 13. Worktree safety

No worktree was created for this release. The repository has exactly one worktree, and the
`v0.4.0` worktree used in the previous cycle was removed.

The unsafe pattern is recorded in [maturity-plan.md](../development/maturity-plan.md): a worktree
whose `node_modules` is a **Windows junction** must never be removed recursively, because removal
follows the junction — and then npm's own workspace junctions inside it, which point at
`apps/api` and `packages/mcp-mongodb` — and deletes both source trees. The two `node_modules/@cerberus/*`
junctions that exist are npm's own workspace links, not a shared-worktree setup.
