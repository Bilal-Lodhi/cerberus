# `v0.3.0` release notes

**Published as a GitHub pre-release** on 2026-09-26. Annotated tag `v0.3.0`, tag object
`af22236626019352bddebe8798a659151af7ec4f`, target
`95b57836b4d879766ad94953323ce5811f50041a`. No npm package, no container image and no hosted
deployment were published, and nothing was marked stable or latest.

> the documentation tree, where `npm run check:docs` verifies them. GitHub resolves relative
> links in a **release body** against the repository root instead, so the published body uses

Cerberus is an experimental research system. It is **not production ready**, makes no
compliance claim, and carries no proof-of-intent claim. `v0.3.0` does not change that.

## Theme: architecture integrity

`v0.1.0` extracted the system into a standalone repository. `v0.2.0` made it survive a
restart predictably. `v0.3.0` makes its **session lifecycle coherent**: one canonical
transition boundary, explicit partial-failure semantics, truthful domain vocabulary,
concurrency-safe state mutation, bounded read and write paths, and deterministic behaviour
under retry, restart and dependency failure.

It adds no new capability a user would notice. It removes several ways the system could
quietly disagree with itself.

## Why this is a minor version, not a patch

`v0.2.0` was published as a pre-release, so a few of these changes are **observable**:

- **`terminate` returns `503`** where it used to return a misleading `404` when the
  persistence layer was unreachable, and **`409 SESSION_CONFLICT`** where it used to
  silently overwrite a concurrent change.
- **`GET /api/v1/guardian/sessions` no longer lists terminated sessions**, and the list's
  `lastEventTimestamp` is now the durable server-written `updatedAt` rather than the newest
  client-supplied event timestamp.
- **Ingest refuses a terminated session** with `409 SESSION_TERMINATED`. A terminated
  session is now terminal.
- **A create past the reference-corpus ceiling is refused** with
  `409 REFERENCE_CORPUS_LIMIT_REACHED`, where it used to be stored and then silently
  excluded from every comparison.
- **`focusLossCount` replaces `fullscreenExitCount`** as the canonical counter name, with
  the old name kept as a deprecated alias.

Under SemVer's pre-1.0 rule a minor version may contain a breaking change, and each of
these gets the changelog entry and the migration note that
[compatibility.md](../compatibility.md) §2 requires. None of them changes what the system
is *for*.

## What landed

### A central session transition boundary

Session status was written by **five independent code paths** — deploy, ingest's
auto-lock, ingest's auto-clear, reactivate, terminate — that ordered their cache and
durable writes **three different ways**, three of which did not inspect the durable write's
result, and none of which validated the current status.

There is now one place a lifecycle status changes, with domain actions rather than a
generic `setStatus`, an explicit transition table, a durable-first order, a
compare-and-set write, a canonical result that distinguishes *applied* / *no-op* /
*refused* / *conflict*, and caches repaired from the durable outcome rather than from the
caller's intent.

**This fixed a P1:** a terminated session used to accept telemetry, advance its durable
counters, and — on a high-risk batch — be moved to `locked`, a state the operator never
chose on a session they had explicitly stopped.

### Truthful partial-failure semantics

Durable evidence is now written **before** the side effects that depend on it. The order
was paid analysis → paid recommendation → notification → status → **assessment**, so a
process death in that window left a durably `locked` session with a delivered alert and no
recorded justification. It is now analysis → recommendation → **assessment** → status →
notification, and a failed assessment write skips both later steps.

Two response fields make a failure visible where it was previously indistinguishable from
success: `telemetryPersisted` (with the accepted/duplicate counts **omitted** when the
store did not answer) and `assessmentPersisted`.

**Notifications remain best effort.** They are not durable, not retried, not ordered and
carry no dedup key. They cannot affect durable state — that was already true and is now
also true of their *ordering*, because they are sent last.

### Durable identity for the paid path's one artefact

`risk_assessments` gained a unique index on `riskAssessmentId`, so a re-analysis of one
incident stores one row. Migration `0002` removes any pre-existing duplicates first, and
the write handles the duplicate-key path rather than pre-checking it, because a
read-then-insert would race.

### A hard corpus ceiling

The 200-document ceiling was a **read** ceiling: a 201st document was accepted, stored, and
then neither listed nor compared against — the operator saw a successful add and detection
saw nothing. It is now enforced at the store with an atomic claim, so concurrent creates
cannot exceed it.

### Truthful vocabulary

`WINDOW_BLUR` incremented the `fullscreenExitCount` counter, so the field name described
one of the two events that produced it. The counter is `focusLossCount`, migration `0003`
renames the durable field, and the incident summary says "focus lost". **No score moves**:
the penalty was always gated on focus being lost.

### Bounded reads

`get_session_review` returns up to 500 micro-events plus every assessment by default, and
ingest — which consults only the session document — was paying for all of it on every
request. Ingest, reactivate and the session list now ask for what they use. For 20 sessions
of 500 events, the list path carries **10 000 event documents fewer** per request.

### One owner for terminal content

`update_session_terminal_content` was a published MCP capability that **no route called**,
so `monitored_sessions.terminalContent` was always absent and the review path recovered the
workspace from a chain of three sources with no rule about which won. The API now writes it
on terminate, and the other two sources are documented fallbacks for *different facts*.

### A stated retry and idempotency contract

[api-errors.md](../api-errors.md) §11 now classifies **every** mutation route as retry-safe,
idempotent (and on what key), non-idempotent, or paid-with-duplicate-spend-risk. The
practical question — *what may a caller safely do after a timeout?* — now has a written
answer per route rather than an implicit one.

Two properties are worth stating explicitly, because they are easy to over-read:

- **Telemetry has retry idempotency, not replay protection.** A batch is stored at most
  once per `(sessionId, eventId)` and the counters are monotonic, so a retry after a
  network ambiguity is safe. The **monitored client supplies `eventId`**, so a client that
  wants to re-send content can send a fresh one. Durable identity makes retry safe; it does
  not make a hostile client honest.
- **The two paid routes remain non-idempotent.** `POST /api/v1/scenarios` and
  `POST /api/v1/auditor/query` re-spend on a retry, and no `Idempotency-Key` was added. §11.1
  records what a key would cost, what the evidence says, and the condition that would change
  the decision.

### Verification that can see real-database behaviour

Four defects in this repository's history were invisible to its own suite for the same
reason: **a test double that did not match the real store.** Three of the four doubles
returned success from `set_session_status` without persisting anything.

One shared, faithful double now replaces all four, and a **42-case contract suite runs
against both it and a real MongoDB**. A new integration suite drives eleven highest-risk
flows through the **real routes, the real tool registry and the real driver**, and a
bounded CI job runs it against a `mongo:7` service and **asserts that nothing was skipped**.

A documentation link and anchor checker now gates `docs/` in CI.

## Upgrade path

Nothing needs to be done to the code. Two things need attention on the database:

1. **Run the migrations.** `0002` removes duplicate risk assessments, and `0003` renames
   the focus-loss counter. Both are ordered, idempotent and fail before mutating; the
   procedure is in [operations/upgrade.md](../operations/upgrade.md), and the dry run is
   `npm run migrate:dry-run`.
2. **If you run more than one instance, stop one before upgrading.** The ledger now carries
   a unique index on `migrationId`, so two runners cannot record the same migration twice —
   but two runners may still *execute* one concurrently. That is safe, because every
   migration is idempotent and fails before mutating, and it is stated plainly in
   [operations/upgrade.md](../operations/upgrade.md#running-migrations-from-more-than-one-process).

Nothing else is required. Every MCP change in this release is an **added optional
argument**, and every renamed field keeps a deprecated alias, so an existing client keeps
working. The deprecated aliases are **not** removed in this release.

## What this release does not claim

- It is **not production ready**. It is an experimental research system.
- It makes **no compliance claim** — not SOX, not AML, not GDPR, not any other.
- It makes **no proof-of-intent claim**. A risk score is an advisory signal for a human
  reviewer, not an accusation and not evidence that anyone did anything.
- It does **not** guarantee detection. Similarity matching is a local phrase-overlap
  comparison against an operator-managed corpus; a match is evidence about phrasing, not a
  finding that anything was copied.
- It provides **no replay protection** against a hostile client. Telemetry has retry
  idempotency only, as described above.
- It provides **no DDoS protection**. Rate limiting is a per-process backstop that runs
  after authentication and does not limit unauthenticated requests.
- It has **no endpoint agent**. All telemetry originates from the browser console, and the
  scope decision is recorded in [development/maturity-plan.md](../development/maturity-plan.md).
- It has **no accounts, roles or tenancy**, and no per-user attribution. One shared operator
  key, by design.
- It is **not deployed anywhere**, and no package or image was published. It is not marked
  stable or latest.

## Known limitations

The full list, with reasons, is in
[development/architecture-integrity-checkpoint.md](../development/architecture-integrity-checkpoint.md#what-remains-and-is-accepted).
The ones most likely to matter to an operator:

- Rate limiting is a **per-process backstop**, not DDoS protection. N replicas enforce up
  to N times the limit.
- The console's API key is **embedded in its web bundle**. Serve it only to trusted
  operators, or front it with a credential-injecting proxy.
- The two **paid** routes are **non-idempotent**: a retry after a lost response re-spends.
  See [api-errors.md](../api-errors.md) §11.1.
- `GET /api/v1/guardian/sessions/:sessionId` has **no durable fallback** immediately after
  a restart, until something calls the live list.
- A **partial deletion** is reported as complete: the session document is removed together
  with its events and assessments, and the adapter reports only the session's count.
- Notifications are **best effort**, as stated above.
- No backup automation: the scripts are verified, but nothing schedules them, stores them
  off-host, or provides point-in-time recovery.
